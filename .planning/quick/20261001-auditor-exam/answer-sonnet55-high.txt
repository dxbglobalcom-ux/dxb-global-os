**Claim: "SELECT / WITH / TABLE / VALUES run through a cursor; EXPLAIN never ANALYZE, in any spelling; one read"** (`sol-db-mcp.mjs:97-103`, `DONE-LIST.md` item 3, `00-CEO-DIRECTIVE-AUDIT-TWIN.md` §3)
Verdict: REFUTED
Finding: `classify` refuses EXPLAIN only when the literal text `analy[sz]e` appears (`sol-db-mcp.mjs:101`). PostgreSQL decodes Unicode-escaped identifiers before it reads option names, so `EXPLAIN (U&"analy\007Ae") SELECT …` has no match in the regex and executes the statement. That breaks the done-list's own "any spelling" claim. Impact is bounded: only the role's privileges and the READ ONLY transaction limit what runs. It is still a statement executed outside the cursor path, with no 200-row fetch, on a tool whose documented rule says it never executes.
Evidence:
- sql_read `EXPLAIN (U&"analy\007Ae") SELECT pg_sleep(0.01)` returned `(actual time=10.054..10.055 …)` and `Execution Time: 10.060 ms`.
- The plain `EXPLAIN (ANALYZE) SELECT 1` was refused, so only the escape slips through.
- Offline, `m.classify('EXPLAIN (U&"analy\007Ae") SELECT 1')` returns `{mode:"plain"}` with no refusal.
- The tool log shows `EXPLAIN (U&"\0061nalyze" true) SELECT 1` was accepted earlier on 2026-10-01.
Correction required: B. Allow-list the EXPLAIN options instead (accept only `COSTS`, `VERBOSE`, `FORMAT` and similar, and refuse the rest), or refuse any `U&`, quoted or non-ASCII byte inside an EXPLAIN option list. Add test 4 cases for the escape.

**Claim / done-list item 3: caps of "4 KB per cell, 64 KB per answer, 200 rows"** (`sol-db-mcp.mjs:140-144, 199-204, 186`)
Verdict: REFUTED
Finding: The caps are applied in the tool's own process after PostgreSQL has already sent everything, and they count characters, not bytes. `FETCH 201` pulls up to 201 full rows into a Node string before any cut, so one query such as `SELECT repeat('x',1e8) FROM generate_series(1,201)` means about 20 GB arriving in Sol's tool process. That can kill the MCP server or the host, which `x230-freeze-swap-orphans` says already has memory limits. The only bound is the 10 s timeout. Separately, `s.length` and `text.length` count UTF-16 units, so a 4096-character cell of 4-byte characters is about 16 KB. The "64 KB" answer can reach about 256 KB.
Evidence:
- sql_read `SELECT repeat('x', 20000000)` returned the full-width cut marker `[cut at 4096 of 20000000 chars]`, so all 20 MB crossed the wire and was decoded first.
- Test 6 only uses a 1 MB cell and `generate_series(1,10000)`, so no exhaustion item exists.
- The main checkout's later commits (`3c8517d7`, `f73c5d4a`, `f193f852`, `79b2b40b`) add byte caps and a 16 MB wire guard. They are not in this diff and I did not audit them.
Correction required: B, and it is already repaired in later commits. Bound the transfer itself (wire guard) and count bytes. Add an exhaustion test, for example 201 rows of a 5 MB cell.

**Claim / done-list item 8 (R7): `refuter.sh --proof` prints `DB_WRITE_REFUSED` ×3, so the role refuses writes**

Attempts #2 and #3 count as refused when the tool fails to log in (wrong credential, wrong user), because the error is `isError` text.
