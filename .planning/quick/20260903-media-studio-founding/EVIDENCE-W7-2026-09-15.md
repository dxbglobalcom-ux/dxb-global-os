## 3. THE MIGRATION — AND THE TRAP INSIDE IT

`db/migrations/20260915003000_w7_media_voice_kind_removed.sql`.

**The trap, found while writing it:** a CHECK constraint added the ordinary way **validates existing rows**. Five
`kind='voice'` rows exist. The migration would have been refused by the database — or, worse, invited a later
session to "fix" the problem by deleting them. The constraint is therefore added **`NOT VALID`**: new rows are
checked, the logbook is left alone. The migration says so in its own header, and a guardrail block re-reads the
constraint and counts what survived:

```
$ pnpm construction:schema
NOTICE:  W7: kind CHECK shut; 0 historical voice row(s) kept (W12 owns their removal)
[bootstrap] done — applied 1, skipped 166, ledger total 167

$ (the company engine, through the same canonical chain)
NOTICE:  W7: kind CHECK shut; 5 historical voice row(s) kept (W12 owns their removal)
[bootstrap] done — applied 1, skipped 166, ledger total 167
```

The two NOTICE lines differ exactly as they should: the construction engine's data is generated and holds none of
the holding's rows; the company's holds the five real ones.

After, both engines:

```
supabase_db_DxB_Global_OS: CHECK ((kind = ANY (ARRAY['still','shoot','upscale','assemble','probe']))) NOT VALID
supabase_db_DxB_Build:     (identical)
$ select count(*)||'|'||statuses||'|'||ids-md5 from media_jobs where kind='voice'
5|done|9ffe4755d860e7396420dab31271a636      ← byte-identical to the baseline
```

### ROLLBACK

In the migration's header: drop the constraint, re-add it with `'voice'` in the array, restore `voiceEngine` and its
`ENGINES` key in `media-lane.ts` and the params/description/enum in `media.ts`, rebuild, **and restart
`dxb-scheduler`** — the lane is code the daemon holds in memory (§6).
