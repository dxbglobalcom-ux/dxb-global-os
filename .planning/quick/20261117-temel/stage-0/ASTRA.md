## 1. Independent cut, written before opening BUILD.md

The bench must prove four things. A write can reach only the designated construction target. The foundation can be built from an empty foundation state and upgraded over populated data. The old and new systems can coexist with measured boundaries for tables, roles, clocks and broadcasts. The lead can tell whether the exact candidate passed the tests the lead committed.

I would cut the work in this order.

1. Complete the folder disposition and board scan. Show the deletion list to the CEO first. Read the old contracts before signing each piece’s tests.
2. Establish the trusted test runner, then prove the target identity and teardown boundary before permitting destructive tests.
3. Build the chain in small pieces. Prove file-and-ledger atomicity, immutable history, function replacement, reference replay and serialized execution.
4. Install the roles. Prove clean installation, populated upgrade and semantic snapshot equality. Test coexistence from real connections in both directions.
5. Add the liveness table and the additions report. Try the in-process tool door and usage accounting separately. Keep runtime behavior with its first real user.
6. Run the integrated proof and the unchanged legacy battery. Preserve the individual verdicts and have the stage commits audited.

A cut is too small if a damaged test harness, a missing migration or an unauthorized grant can still produce green. It is too large if it needs a resident engine, an office declaration system or a screen. Each piece must leave enough of the session’s 45% budget for the lead to verify and commit it.
